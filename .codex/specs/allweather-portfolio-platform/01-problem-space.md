## 1. Problem Statement

現有 `finance_algorithms` 只是一個**無狀態純計算器**:給定單一標的的「總預算 + 觸發價→終止價 + 交易次數」，算出左側加碼(等差/等比金字塔)的每階部位。它解決的是「**怎麼買進單一標的**」，完全沒有觸及「**該買什麼、各買多少、何時調整**」。

使用者要的是往上跳兩層的能力:一個 **總經驅動、ML 輔助、全球多資產的全天候投資組合平台**，以「左側交易者」哲學(在週期低點分批佈局)為核心，產出**月到半年為單位的再平衡決策**。

## 2.5 使用者真實投資組合(As-Is portfolio)與核心痛點

> 使用者於 2026-06-09 提供。這是配置改造的真實起點與成功衡量基準。

- **現況持倉:** 股票部位中 台股 ≈ 50% + 美股 ≈ 50%,**大多為科技股**。
- **核心痛點:** 集中於科技股 → **高 beta、單一風險因子集中、跨持倉高相關、波動大**;缺乏跨資產類別的對沖與平衡。
- **明確目標(可量化的最佳化問題):** 設計更好的資產配置,使 **beta / 風險溢價(risk premium)/ 波動(volatility)** 三者取得平衡。
- **意涵:** 全天候配置在此的具體任務 = 以平衡資產(債/黃金/大宗/現金/加密等)稀釋科技股的高 beta 集中度,在可接受的預期報酬下降低組合波動與回撤。這直接定義了 Epic C(配置最佳化目標函數)與 Epic D(各資產配重預期)的需求。

### 最佳化目標函數(使用者 2026-06-09 確認,Gap#3 部分關閉)

- **目標:** 最大化 **3~5 年累積報酬**(中期、總報酬導向,非年年穩定)。
- **硬約束:** 年化波動 ≤ **30%**(明確上限,「再大承受不了」)。
- **形式化:** `maximize E[3~5yr cumulative return] s.t. annualized_vol ≤ 30%`。
- **重要反轉:** 30% 年化波動屬「高」水準(約等於現有科技股組合的波動)。故真實意圖**不是降低總風險**,而是「**在既有風險上限內最大化報酬**」= 衝高 risk-adjusted return / Sharpe。與最初「想要低 beta/低波動」的說法不同,**以此數字為準**。
- **最大回撤容忍(2026-06-09 確認):** **-50%**(帳面虧損達 -50% 為棄船底線)。Gap#5 關閉。
- **風險屬性結論:** 目標=最大化中期報酬、vol 上限 30%、可忍 -50% 回撤 → **積極成長型投資人,高風險承受度**。

### ⚠️ 命名與哲學矛盾(待使用者裁決)

使用者的數字(最大化報酬、30% vol、可忍 -50% DD)描述的是**積極成長型**配置。但「**全天候 (All-Weather)**」在投資學上是 **Dalio 式的資本保全、低波動(目標約 10~12% vol)、在所有總經環境都求生存** 的哲學——兩者**根本對立**。

**裁決(2026-06-09):使用者選 (A) 積極成長 + 風險上限。**
- 「全天候」僅是借名;真實意圖 = **高 Sharpe 的積極成長組合**。
- **科技股仍為主力引擎**;其他資產(債/黃金/大宗/現金/加密)作為**風險預算管理工具**,用以把組合壓在 vol ≤ 30%、maxDD ≤ -50% 的天花板內。
- **不是** Dalio 式等風險平價全天候;是**成長傾斜 + 衛星風險管理**。
- **命名建議:** 專案名「全天候」具誤導性,建議改為「**風險預算下的積極成長配置 (Risk-Budgeted Aggressive Growth Allocation)**」或類似,避免與 Dalio All-Weather 混淆。(待最終確認)
- **對下游影響:** Epic C 目標函數=報酬最大化 + vol/DD 硬約束(非 risk-parity);Epic D 的 regime 預測服務於「何時加減碼風險、輪動成長曝險」,而非「維持全天候平衡」。

## 2.6 ⭐ 真實專案動機與成功定義(2026-06-09 重大重構)

> 使用者坦白:這**不是**以賺錢/打贏 benchmark 為目的的系統。真實動機如下,推翻先前以「最佳配置」為核心的框架。

**真實北極星 = 打造一個個人 quant 研究/練功平台。** 使用者明確意圖:
1. **練各種 ML/DL 模型**(模型本身是目的,不是手段)。
2. **能跑嚴謹回測**(驗證任意策略/模型)。
3. **(未來)下沉到個股等級**的選股與投資組合。
4. **(未來)拉高交易頻率衝 beta**(故「月~半年再平衡」只是起點,非終態)。

### 成功定義重構(取代原本以報酬為主的 Gap#3)
- 成功 ≠ 報酬贏過 benchmark。
- 成功 = **(a)** 能快速、低摩擦地實驗多種模型;**(b)** 回測引擎可信(無 lookahead / survivorship / 不真實成交);**(c)** 架構可從 資產類別 → 個股 → 變動頻率 平滑擴展。

### 雙目的(2026-06-09 使用者新增):作品集 + 投資研究 lab
- 本專案同時是 **(1) 對外作品集 / portfolio showcase** 與 **(2) 個人投資研究 lab**。
- **新增一級 NFR(由作品集驅動):** 程式可讀性、文件/README、可重現性(seed/資料版本/config)、可展示的端到端敘事、前端展示面(Epic F 升值)、工程衛生(測試/CI/結構)。廣度(三框架/MLOps/回測嚴謹度)成為**展示賣點**。
- **兩速結構(解雙目的衝突):** lab 層快速髒實驗;其上維護一層**策展 showcase**(乾淨 demo + writeup + 打磨過的 vertical slice)。避免整個 repo 皆半成品。
- **作品集差異化武器 = 一路 grill 出的方法論嚴謹度:** point-in-time 回測、誠實 baseline 比較、event-study 標註 n + CI、稅/匯/成本後報酬。這些正是業餘 quant 作品集最缺、最能脫穎而出之處。
- **⚠️ R1 反轉(作品集情境):** 對作品集,**完成的深度 > 未完成的廣度**。5 個半成品 < 1 條打磨到底、端到端、有誠實結論的 pipeline。→「先把第一條 vertical slice 做完做亮」從建議**升級為硬需求**。

### 連帶裁決
- **「ML 打不贏靜態就砍掉」(前一輪 #6)→ 作廢。** 使用者選 (B):ML 是目的,不論勝負都要保留。Epic D/E 為**第一級目標**,不是可選項。
- **「全天候配置」→ 降級為「第一個練手策略 (strategy #1)」**,非專案終點。專案是 **strategy/model 實驗平台**,全天候只是 seed 題目。
- **回測引擎 → 升級為 foundational 皇冠鑽石**,優先序高於任何花俏模型(見 §6 重排)。

### ⚠️ 已識別的最大專案風險
- **R1 — 無止盡 yak-shaving:** 「玩遍所有模型」若無里程碑/結束條件 → 永遠蓋不完的研究大雜燴。**緩解:每個 epic 綁定可驗收的 capability milestone,而非開放式探索。**
- **R2 — 回測謊言污染一切:** 業餘 quant 回測 90% 有靜默錯誤(lookahead / survivorship / 不真實 fill)。回測一錯,所有「學到的」模型都在學垃圾。**緩解:point-in-time 正確的資料層 + 嚴謹回測引擎必須先於任何模型(見下一輪 grill)。**

## 4. To-Be 願景(使用者確認的範圍)

全自動 data-driven、端到端平台,含 **6 個子系統**:

1. **Data / Crawler** — 台灣 + 國際公開 API;資產價格 + 總經(財政政策、FED 升降息)+ 長期氣候(El Niño);資料版本/設定管理。
2. **Computation** — 全天候配置、多期(短/中/長)、再平衡訊號(月~半年)、(設計階段決定)是否接金字塔做進場執行。
3. **ML/DL + MLOps** — 三段式:資產循環週期 phase 偵測 → 各資產配重預期 → 最佳投資組合;含訓練、推論、監控、資料/模型設定管理。
4. **Persistence** — 投資組合狀態、再平衡歷史、資料/模型 lineage。
5. **API Backend** — FastAPI(沿用擴充)。
6. **Frontend** — Next.js(全新)。

### 資產範圍
全球多資產(全天候原型):股 / 債 / 大宗商品 / 貴金屬 / 加密貨幣 / 台幣現金定存 / 美金現金定存 / …

### ML 目標(三層)
1. 市場狀態預測:各資產類別「現在處於投資循環週期哪個 phase + 短期 phase 變化」。
2. 當下各資產配重預期。
3. 最佳投資組合輸出。

## 6. 建議的 Epic 分解(使用者已選「分 epic 分階段」)

> **依 §2.6 重構後重排。** 因真實目標=練模型 + 可信回測,**回測引擎與 point-in-time 資料層升級為地基(Epic A0/A)**,優先於任何模型。全天候=strategy #1。個股/高頻為 future scope,設計需預留擴展但不在前期實作。

- **Epic A0 — Point-in-Time 資料層 + 嚴謹回測引擎(NEW,最高優先)**
  正確處理 lookahead / survivorship / 成交與成本模型;策略無關的回測 API(吃任意 allocation/signal,吐報酬/vol/maxDD/Sharpe 等績效)。**這是 R2 的緩解,是整個練功平台可信度的根基。**
- **Epic A — Foundation / Thin Vertical Slice(緊接 A0)**
  最小端到端:單一公開源抓 5~6 個資產類別 proxy + 2~3 個總經指標 → **規則式(非 ML)** 靜態全天候配置 + 簡單 regime 標籤 → 持久化最新快照 → 1 個新 API endpoint → 最小 Next.js 頁顯示「當前目標配置 + regime」。**目的:打通管線、驗證資料可得性與架構,風險最低。**
- **Epic B — Data Platform / Crawler**
  多源整合、總經(FED/財政/氣候)、資料版本與設定管理、儲存 schema、缺值/頻率對齊。
- **Epic C — Portfolio Computation Core**
  全天候配置、多期(短/中/長)、風險配置(risk parity 等)、再平衡訊號(時間 + regime 觸發)、**與金字塔模組的整合決策**(進場執行)。
- **Epic D — ML/DL 週期與配置**
  (1) regime/週期 phase 分類 →(2)各資產預期報酬/風險 →(3)組合最佳化。建議**從 regime 分類起步**,逐層替換 Epic A 的規則式邏輯。
  - **D-feature: 事件驅動模型族(Event-Driven,2026-06-09 使用者新增)**
    需求原意:重大人類歷史事件(開戰 / 科技 hype-cycle / 極端氣候如 Godzilla 級 El Niño)有**可重演的類型**,對特定**產業/區位**有中長期趨勢影響;希望有 ML + 回測 + 建議判斷。
    - **誠實重構(避免「ML 預測黑天鵝」的不可能):** = **事件類型分類學 + 歷史類比庫 + 事件研究(event-study)回測**。
      - ML 真實角色:**(a)** NLP/文本分類偵測「某已知類型事件正在發生」;**(b)** event-study 統計同類型歷史事件對產業/區位的中長期影響分布;**(c)** 輸出**標註樣本數 + 信賴區間**的建議(如「基於 N 個歷史類比,事件後 6~18 個月 XX 產業中位數報酬 ±range」),不偽裝成確定預測。
    - **硬限制 D-E1(統計):** 稀有事件 n 極小(每類僅數次)→ 正規監督式 ML **必然過擬合**;以 event-study / case-based / 貝氏小樣本方法為主,**禁止**用 n=5 訓練深度模型假裝有預測力。
    - **硬限制 D-E2(lookahead):** 「事件起點」標籤是後見之明 → 必須走 A0 point-in-time 紀律;訓練/回測嚴禁用上帝視角貼標。
    - **硬限制 D-E3(非平穩):** 「同類但每次不同」(2000 vs 2021 vs 2023 科技泡沫)→ 產出須呈現分布與離散度,不可只報單點。
    - **相依:** 重度依賴 A0(point-in-time)+ B(總經/氣候資料)+ G(alt-data/NLP 文本)。**不建議作為起手模型**(最難、樣本最少、最易過擬合)。
- **Epic E — MLOps Pipeline**
  資料/模型設定管理、訓練、推論服務、監控/drift。
- **Epic F — Frontend(Next.js)**
  配置 / regime / 再平衡建議儀表板。
- **Epic G — Alternative Data(OPTIONAL / 另開戰線,2026-06-09 使用者標記)**
  輿論/情緒資料 + GenAI/NLP 情緒分析;(更後期)衛星等另類數據。**明確 optional、不在關鍵路徑、獨立 branch/lane。** 對練功平台而言是合理的 NLP/GenAI 模型練習場,但 edge 高度不確定。
  - **綁定條件 G-C1:** 所有 alt-data 必須走 Epic A0 的 point-in-time 紀律(新聞/社群時間戳 ≠ 可讀取時間,情緒分數不得事後重算回填)→ 否則為假 edge 頭號來源。
  - **綁定條件 G-C2:** 必須綁可驗收 milestone(R1 重災區),禁止開放式探索。

(API backend 擴充與 Persistence 跨各 epic 漸進實作,不獨立成 epic。)

### 多框架需求(2026-06-09 使用者確認:PyTorch + TensorFlow + JAX 三者都要用)
- **定位:一級學習目標**(吻合「練各種模型」北極星)。三框架皆須可在平台上實驗。
- **架構保證(成本≈0 的關鍵):** A0 回測引擎 + Tier2 追蹤對「產出訊號的框架」**完全無感**,只吃標準化輸出(signal/weight 序列 + metadata)。任何模型遵守薄介面(`fit`/`predict`/`generate_signal`)即可,底層 PyTorch/TF/JAX/sklearn/statsmodels 皆可。框架差異封裝在模型內部,不污染 harness。
- **⚠️ 護欄(技能 vs 績效):** 三框架是**技能目標非績效目標**——同模型跨框架結果幾乎相同,框架不帶來 alpha。**禁止把同一模型港三遍**(R1 yak-shaving)。建議**不同框架練不同模型族**:PyTorch→LSTM/原型;JAX/Flax→Transformer + 大規模平行 sweep(環境有 `jax-dev-skill`,適合反台積電 sweep);TF→serving/TFX 生態(對接延後的 Tier3)。
- **⚠️ Tier1 ops 需求:** PyTorch/TF/JAX 各綁不同 CUDA/cuDNN → 同環境易衝突。**每框架獨立環境隔離(分 venv 或分容器映像)**,平行排程器須能挑對應映像。列入 A0/Tier1 驗收。

### Decision log(逐輪 grill 結果)
- 資料正確性策略 = **C(混合)**:先用粗糙回測(收盤價/無成本/現存標的,**明知數字為假、僅驗證 pipeline**)跑通端到端;**在下沉個股 / 拉高頻率之前,強制把 Epic A0 補到 point-in-time 正確**。
- **起手模型 = LSTM**(使用者覆蓋「先做笨 baseline」建議,選 LSTM 為第一個實作模型)。
  - **首個具體實驗 = 台積電(TSMC 2330)反指標 / 對衝訊號**(待確認標的拼字)。此實驗同時作為 Epic A0/A 的 thin vertical slice 錨點。
  - **baseline 重構:笨 baseline 不是「之後才做的 roadmap 步驟」,而是衡量尺。** 它幾乎免費,且必須與 LSTM 在**同一 A0 回測 harness**並存,否則「LSTM 有沒有學到東西」無法回答。→ baseline 併入 DoD,不可跳過。
  - **⚠️ 方法論警示(接受選擇但設護欄):** LSTM 在金融時間序列上**極易過擬合**(低訊噪比、非平穩、樣本有限)。護欄:強制 **walk-forward / out-of-sample 驗證** + 對笨 baseline 的並排比較,否則華麗的 in-sample 曲線會自我催眠。
- **Definition of Done(已鎖定):** 任一模型 = 能在 A0 回測引擎產出**可與笨 baseline 並排比較的 out-of-sample 績效報告** → 即 DONE。
- **MLOps / 實驗速度 = 一級需求(使用者第 3 點):** 目標是「系統化實驗 + 加快實驗腳步」。意涵:標準化 model/strategy 介面(任意模型即插即用同一 backtest harness)、實驗追蹤與可重現(seed / 資料版本 / config)、對 baseline 的 leaderboard。→ Epic E 從「維運」升級為「**實驗加速器**」。
  - **⚠️ 排序護欄 R3(過度工程)— 2026-06-09 經使用者反駁後精修:** 原版「跑通第一個實驗前不要碰任何 MLOps」**過粗,已收回**。使用者正確指出:第一個實驗(找反台積電對衝標的)本身就是**對整個股票宇宙的大規模平行 sweep**,不是 single run。故將 MLOps 拆三層:
    - **Tier 1 — 平行運算底座**(Ray/Dask/joblib/multiprocessing/GPU 批次):**地基,馬上要,併入 A0**。反台積電 sweep(上千檔滾動相關/beta/共整合 + 數百候選模型)逼著平行化。
    - **Tier 2 — 輕量實驗追蹤**(每 run 的 config + OOS 指標寫入可比較結果表 + leaderboard):**一旦平行化就要,併入 A0**。N 個平行結果無法用肉眼比較。
    - **Tier 3 — 完整 MLOps 平台**(model registry / 自動重訓 / drift 監控 / serving / CI/CD / 生命週期治理):**延後**。尚無模型「上線」需治理 → 蓋此層才是過早抽象。等手痛過一次再從痛點萃取。
  - **連帶修正 thin-slice 定義:** 第一條 vertical slice = **平行 sweep**(非 single run):反台積電候選篩選(Tier 1)→ 每候選 LSTM 訊號 → A0 回測 → OOS 指標寫入 leaderboard(Tier 2)vs 笨 baseline。A0 必須**從第一天就具平行能力 + 輕量追蹤**。
  - **R3 對 §6 epic 順序的影響:** A0 範圍擴大,內含 Tier 1(平行底座)+ Tier 2(輕量追蹤);原 Epic E(MLOps)縮窄為 **Tier 3 專屬**,維持延後。

## 7. DoR Gaps — 進入 Requirements 前必須關閉的未知

> 這些是阻擋 spec 動工的關鍵問題,屬下一輪(各 epic 的 requirements elicitation)。

1. **使用對象與合規**:個人自用 / 研究,還是對外產品?後者觸及台灣金管會投顧、機器人理財規範 — **影響整個法規與 NFR 範圍,最高優先。**
2. **執行邊界**:系統只「建議配置」,還是要「實際下單」?接不接券商?
3. **成功指標**:用什麼判斷成功?回測 Sharpe / 最大回撤 vs benchmark(60/40 或 buy-and-hold 0050)?要有目標數字。
4. **風險限制**:可容忍最大回撤、各資產上限、是否允許槓桿/做空?
5. **再平衡觸發規則**:純時間(月/季)、漂移帶(drift band)、還是 regime 變化觸發?或混合?
6. **資料歷史深度**:各資產類別可取得的歷史長度(加密貨幣短)→ 限制 ML 訓練與回測期間。
7. **金字塔整合**:Epic C 中,portfolio 決定預算分配後,各資產進場「是否」一律走金字塔?還是僅左側資產走?

## 8. 假設(暫定,待驗證)

- A1:個人自用 / 研究用途(故暫不納入對外投顧合規)— **待 Gap#1 確認,可能推翻。**
- A2:系統產出「建議」,不自動下單(無券商整合)— 待 Gap#2 確認。
- A3:benchmark 暫定為全球 60/40 與 buy-and-hold 0050 雙基準。
